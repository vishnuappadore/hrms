## Purpose

Manage all employees working across salon branches — barbers, receptionists, cashiers, supervisors, managers. Create staff records, maintain employment details, configure salary and commission structures, assign system roles, and monitor employee performance (ratings, revenue, services completed). Every staff member created here becomes available for assignment in operational modules — Appointments and Walk-in Queue. Bilingual EN + AR (RTL); currency OMR with 3 decimals (baisa).

## Primary users / permissions

Super Admin, HR, Operations Manager, Branch Managers (assigned branches). System access (role/status/password) is granted by admins. Guards use `@Permissions(...)` + `@BranchScoped(...)`; list queries scope through `getEffectiveBranchIds()`.

## Screens & flows

### 1. Staff Dashboard (list)

**Summary cards** (operational statistics across all branches)
1. **Total Staff** — total number of *active* employees across all branches.
2. **Average Rating** — average customer rating of all service staff.
3. **Top Performer** — highest-performing staff member based on configured performance metrics.
4. **Monthly Payroll** — estimated payroll amount for the current month (sourced from salary structures + [[payroll]] period calc).

**Search** — by Staff Name or Mobile Number. The list updates dynamically while typing.

**Filters**
- **Branch** — employees belonging to a selected branch.
- **Role** — filter by role/designation.

**Table columns** (one row per employee)
1. **Staff** — Avatar, Employee Name, Mobile Number.
2. **Role** — designation (e.g. Senior Barber, Barber, Junior Barber, Receptionist).
3. **Branch** — assigned branch.
4. **Employment Type** — Full-time | Part-time | Contract.
5. **Rating** — average customer rating.
6. **Revenue** — revenue generated by the employee during the reporting period.
7. **Actions** — **Reset Password** (opens a dialog to set a new password for the staff member's login; revokes all of their active sessions) and **Edit** (opens the record for modification via the same 4-step wizard). **View Staff Profile is not yet built** (see §3) — there's no separate View action in the list today.

### 2. Add New Staff — 4-step registration wizard

`+ Add Staff` launches a four-step wizard that collects all employee information in a structured sequence: **Basic Profile → Employment → Salary & Commission → System Access → Add Staff**. There is **no Save Draft** — the wizard is completed in one pass (Close cancels).

#### Step 1 — Basic Profile
Collects the employee's personal information and login identifier.
1. **Staff Name** * — employee's full name. *Required.*
2. **Username** * — login identifier, unique per tenant. *Required.* Moved here (next to Staff Name) from System Access — the account is effectively created from this step onward, and login-identity fields belong with identity, not access config. Checked live against the tenant's existing staff as the admin types (before submit) — see Business rules.
3. **Mobile** * — contact number; used for communication and identification. *Required.*
4. **Email** * — official email; used for notifications and system communication. *Required.* Checked live for uniqueness the same way as Username.
5. **Gender** * — `Male` | `Female`. *Required.* Defaults to `Male` for a new staff member.
6. **Status** * — `Active` | `On Leave` | `Inactive`. Controls staff availability throughout the system. *Required* (always has a value — defaults to `Active`).
- Field errors are specific per-field messages (e.g. "Enter a valid mobile number", not a generic "invalid value"), and clear automatically as soon as the field becomes valid — no need to leave the field or resubmit.
- Navigation: **Next** → Employment; **Close** cancels.

#### Step 2 — Employment
Defines the employee's organizational information.
1. **Primary Branch** * — assigns the employee to their main salon branch for operational purposes. *Required.* Distinct from System Access's **Assigned Branches** (which controls system/data access, can span multiple branches or all of them) — the Primary Branch is always included in Assigned Branches and **cannot be deselected** there (see Step 4).
2. **Role** — job designation (e.g. Barber, Senior Barber, Receptionist, Manager); determines operational responsibilities. Same underlying field as Step 4's **User Role** — editing either updates the other.
3. **Employment Type** * — `Full-time` | `Part-time` | `Contract`. *Required.*
4. **Joining Date** — official start date; used for HR and payroll calculations.
5. **Reporting Manager** — another staff member this person reports to; supports organizational hierarchy. Searchable picker, narrowed to staff who have access to the selected Primary Branch (assigned to it directly, or via All-Branches Access) — until a Primary Branch is chosen, all staff are offered. A person cannot report to themselves; a previously chosen manager is cleared automatically if changing the Primary Branch makes them ineligible.
- Navigation: **Back** → Step 1; **Next** → Salary & Commission.

#### Step 3 — Salary & Commission
Defines the employee's salary structure.
1. **Base Salary** — monthly fixed salary, in the currency of the staff member's **Primary Branch** (Step 2) — not a hardcoded tenant-wide currency. Falls back to the tenant's default currency before a Primary Branch is chosen. *(Stored as integer minor units.)*
2. **Commission Enabled** — toggle. When enabled, commission fields become available.
3. **Commission Rate (%)** — percentage commission applied to eligible sales/services (only when Commission Enabled).
4. **Allowances** — a dynamic multi-allowance list. Each row picks a **type** from the tenant's configurable catalog (Settings › Payroll Components — see below) plus an **amount**; administrators may **add or remove** rows dynamically. Each type can be picked in only **one row at a time** — once selected, it drops out of the other rows' pickers (freed again if that row's selection is changed or the row is removed). *(Each amount stored in minor units.)*
5. **Statutory Deductions** — a second dynamic list, same shape as Allowances (including the one-row-per-type rule) but drawing from the catalog's deduction types (e.g. Social Insurance/PASI). **Supersedes the prior open question** — deductions DO live on the staff record, not only in `[[payroll]]`.
6. **Gross / Net summary** — **auto-calculated, read-only**: `Gross = Base Salary + Σ Allowances`, `Net = Gross − Σ Statutory Deductions`. Computed on read, never stored (avoids drift if base salary or component amounts change later).
- Navigation: **Back** → Employment; **Next** → System Access.

**Settings › Payroll Components** (new, under [[settings]]): a tenant-configurable catalog of allowance/deduction types, each with a **basis** — a fixed amount in the tenant's default currency, or a percentage of base salary (e.g. PASI defaults to 7% of base). Selecting a type in Step 3 prefills the row's amount from the type's default (resolving a percentage basis against the employee's entered base salary via `packages/shared/src/money.ts`'s `percentOf`), but the admin can edit it — the staff row always stores a concrete snapshot amount, never a live-recomputed percentage. A **fixed-amount** default is only auto-filled when the staff member's Primary Branch currency matches the tenant's default currency (the catalog has no per-branch pricing); otherwise the amount is left blank for the admin to enter manually, rather than silently prefilling a value minted in the wrong currency. Types are never hard-deleted, only deactivated, so existing staff rows keep a valid reference after a type is removed from the picker.

#### Step 4 — System Access
Final stage. Defines the employee's application access: system role, account status, branch accessibility, and login credentials. Two sections:

**Section A — Role & Branch Access**
1. **User Role** * — dropdown, required. Determines the employee's functional permissions. Detailed permissions per role are managed in the Roles & Permissions module ([[settings]] / RBAC), not here. Same field as Step 2's **Role**.
2. **Status** * — dropdown, required. Account status: `Active` (can log in, access assigned modules, available for operations) | `Inactive` (login disabled, cannot access system; historical records remain unchanged).
3. **All-Branches Access** — toggle. When **enabled**, the employee can access every branch in the organization and branch selection is **not required**. When **disabled**, the employee is restricted to only the branches chosen in **Assigned Branches**.
4. **Assigned Branches** — branch selection shown/required only when All-Branches Access is off. The **Primary Branch** chosen in Step 2 always appears here pre-checked and **locked** (its checkbox is disabled) — it cannot be removed from Assigned Branches while All-Branches Access is off. Enforced both client-side (checkbox disabled) and server-side (the API rejects a save that would leave the Primary Branch out of Assigned Branches).

**Section B — Login Credentials** (creates the application login account; **create-only**)
1. **Password** * — required. Stored securely (encrypted / argon2id hash). Validation: **≥ 8 characters, ≥ 1 alphabetic character, ≥ 1 numeric digit**. Policy may be extended per company security settings.
2. **Confirm Password** * — required; must exactly match Password before the account can be created.

*(Username moved to Step 1 — Section B now holds only Login Credentials.)* This whole section is shown **only when creating a new staff member** — it's hidden entirely in Edit Staff, since there are no password fields to prefill/edit here. Changing an existing staff member's password goes through the dedicated **Reset Password** dialog from the Staff Dashboard list (see §1), which also revokes their active sessions.

- Navigation: **Back** → Step 3 (preserving all entered information); **Add Staff** (submit).

**Add Staff (submit)** validates all four steps, then: creates the staff profile; creates the employee login account; assigns the selected User Role; assigns branch access (all-branches or the selected branches); applies the account status; saves login credentials securely; makes the employee available throughout the system per the configured access. The Staff Dashboard refreshes to show the new employee.

## Data model / fields

- **Staff record / profile**: full name (req), username (req), mobile (req), email (req), gender (req, `male|female`), staff status (req, `active|on_leave|inactive`), primary branch (req), role/designation, employment type (req, `full_time|part_time|contract`), joining date, reporting manager (FK to another `users` row). "req" fields are enforced by the API's create schema going forward; the underlying columns stay nullable at the DB level (pre-existing records created before this requirement keep whatever they have).
- **Salary structure**: `base_salary_minor` (BIGINT baisa), `commission_enabled` (bool), `commission_rate_pct` (Decimal(5,2)), allowances and statutory deductions (each a row `{ payroll_component_id, amount_minor }` referencing the tenant's Payroll Components catalog), `gross_salary`/`net_salary` (derived = base + Σ allowances / gross − Σ deductions; always computed via `packages/shared/src/money.ts`, never stored).
- **Payroll Components catalog** (Settings, tenant-configurable): `{ category: allowance|deduction, name_en, name_ar, basis: fixed_amount|percentage_of_base, default_amount_minor | default_rate_pct, is_active }`. No hard delete — removing a type just deactivates it.
- **System access**: `user_role` (FK to `roles`), account status (`active|inactive`), `all_branches_access` (bool), assigned branches (`user_branch_assignments`), password hash (argon2id), username (kept — see ⚠️ Changed).
- **Performance (read)**: rating (customer feedback source — see Open Questions), services completed, monthly revenue.
- **Salary history**: not yet built — still planned (see Open Questions/Roadmap); today's salary/commission edits overwrite the current state.

Touchpoints: `users` (email unique per tenant, password_hash argon2id, status, locale, username), `roles` + `role_permissions`, `user_branch_assignments`, `staff_profiles` (1:1 user — mobile/gender/staff_status/employment/salary/commission fields), `payroll_components` (Settings catalog), `staff_payroll_components` (join table: a staff member's selected allowance/deduction rows).

## Status / state machines

- **Staff status** (availability): `Active` | `On Leave` | `Inactive`. Only **Active** employees are available for assignment in Appointments and Walk-in Queue.
- **System account status** (login): `Active` (login enabled) | `Inactive` (login disabled, history preserved). This is a *separate* concept from staff status — see ⚠️ Changed.
- **Employment type** (not a state machine, an attribute): `Full-time` | `Part-time` | `Contract`.

## Business rules

- **Staff Name, Username, Mobile, Email, Gender, Status, Primary Branch, and Employment Type are mandatory** when creating a new employee.
- **Username and Email must be unique per tenant.** Enforced by the API (stable `USERNAME_EXISTS`/`EMAIL_EXISTS` conflict codes on save) and additionally checked **live in the wizard** as the admin types — a duplicate is flagged on Step 1 without needing to complete and submit the whole form. The live check compares against the tenant's already-loaded staff list, so it can miss a match on tenants with more than 100 staff; the API check on save is the authoritative backstop regardless.
- Each employee **belongs to one Primary Branch** (for operational/payroll assignment). System access may additionally grant All-Branches or multiple Assigned Branches, but the Primary Branch is always one of the Assigned Branches — it can't be deselected there, enforced client- and server-side.
- Each employee has **one primary employment role**.
- **Only Active employees** are available for assignment in operational modules (Appointments, Walk-in Queue).
- **Commission is optional** — applied only when Commission Enabled is on.
- **Gross/Net Salary are auto-calculated** — Gross = Base Salary + all configured allowances; Net = Gross − all configured statutory deductions; both read-only.
- **Salary History is planned but not yet built** — today, salary/commission/allowance/deduction edits overwrite the current state (no audit trail yet). *(Reverses the earlier "never overwrite" plan below until the history table lands — see Open Questions.)*
- **System roles determine application access**; detailed permissions are managed separately in Roles & Permissions.
- Changes to branch, role, employment status, or salary structure **take effect immediately** for future operational activities.
- **Password policy**: ≥ 8 chars, ≥ 1 letter, ≥ 1 digit; Confirm Password must match.

## Integrations

- **Appointments / Walk-in Queue** — consume Active staff for booking/service assignment.
- **[[pos]]** — commission settings feed checkout commission calculation (`commission_records` on Pay & Complete).
- **[[payroll]]** — payroll runs read salary structures (base + allowances), commission records, and attendance to compute monthly payroll; the dashboard's Monthly Payroll card estimates from this. Salary-structure config lives here; payroll processing/payslips live in [[payroll]].
- **Roles & Permissions ([[settings]] / RBAC)** — supplies User Role options and permission mapping.

## Engineering notes (invariants)

- **Tenant isolation / RLS**: `payroll_components`, `staff_profiles`, and `staff_payroll_components` all carry `tenant_id` with RLS (ENABLE + FORCE + `tenant_isolation` policy), added in one migration. Runtime connects as `hayryou_app`; all queries through `PrismaService.client` / `withTenantTx()`. `AuthPrismaService` (RLS bypass) only in auth/tenants/seed/tests.
- **Money = integer minor units + ISO 4217**: Base Salary, each allowance/deduction amount, and Gross/Net are `BIGINT` minor units, denominated in the staff member's **Primary Branch** currency (falls back to the tenant's default currency before a Primary Branch is chosen — see Step 3); `commission_rate_pct`/`default_rate_pct` are `Decimal(5,2)`. All arithmetic via `packages/shared/src/money.ts` (`percentOf` resolves a percentage-basis component against base salary) — never floats, never per-row ad-hoc rounding, never mixing amounts from different currencies in one calculation. Worked example (OMR, exponent = 3, for illustration only — substitute the branch's actual currency and exponent): base OMR 380.000 (380000 baisa) + Housing OMR 100.000 (100000) → Gross OMR 480.000; − PASI 7% of base = OMR 26.600 (26600) → Net OMR 453.400.
- **API contract**: zod schemas in `packages/shared` first → `createZodDto` in API → same schema in web wizard forms. Errors use stable `code`s from `ERROR_CODES` (never message-text matching) — e.g. email-conflict, password-mismatch, self-lockout on deactivation, name-conflict on a Payroll Component.
- **Permissions**: `staff.employment.manage` gates the salary/commission/employment write path (alongside `users.manage`); `settings.manage` gates Payroll Components writes; reading the catalog only needs `staff.view`. Deactivating a login revokes sessions; self-lockout guard prevents an admin disabling their own last access.
- **RTL / bilingual**: wizard, list, profile, and the Payroll Components settings screen use Tailwind logical properties only; every screen checked in Arabic.
- **Migrations**: expand → migrate → contract; new tenant tables add RLS in the same migration.
